# Security and licence audit — September 2026

The first run of `docs/roadmap.md`'s EPIC-901 row, 2026-09-18, on `main` at `29dd9e9`.

Run it yourself with `pnpm audit-run`. `docs/security/audit-baseline.json` holds the verdict for each
finding below; this document holds the reasoning. A finding in neither fails the run.

## 1. npm advisories — three, all moderate, none reachable

| id | CVSS | path |
|---|---|---|
| `GHSA-67mh-4wv8-2f99:esbuild` | 5.3 | `packages/db` → `drizzle-kit` → `@esbuild-kit/esm-loader` → `@esbuild-kit/core-utils` → `esbuild@0.18.20` |
| `GHSA-82fw-gwwq-j7x9:vitest` | 5.9 | `vitest@3.2.7`, a root devDependency in ten manifests |
| `GHSA-82fw-gwwq-j7x9:@vitest/mocker` | 5.9 | `@vitest/mocker@3.2.7`, under `vitest` |

**esbuild's** advisory is that its **development server** answers cross-origin requests and returns
the response. Nothing here starts one: `drizzle-kit` uses esbuild to transpile `drizzle.config.ts`
and exits. The real fix is upstream — `@esbuild-kit/*` are deprecated packages and `drizzle-kit` has
to move off them.

**vitest's** is a path traversal through `@vitest/mocker`'s redirect mock, exploitable while a test
run is serving. The patched range starts at `4.1.11`, so the fix is a **major** bump of the test
runner across every package. That is its own change and it is out of scope here, deliberately;
`reviewOn` is 2026-12-18 so the decision gets made rather than deferred again.

### The thing to get right about `pnpm audit --prod`

`pnpm audit --prod` reports all three, through paths like `apps__web>better-auth>vitest`. **That
does not mean vitest is a production dependency.** `better-auth@1.7.2` declares `vitest` and
`drizzle-kit` as **optional peer dependencies**, so pnpm walks the peer edge back to our own
devDependency and prints a production-looking path for a development package.

What is true, and matters more, is in `apps/web/Dockerfile`'s own comment:

> Runner keeps the full pruned workspace, **devDependencies included**, rather than a slim
> `output: standalone` bundle

So `vitest` and `esbuild` **are installed in the production image** — not because better-auth needs
them, but because the image ships the whole workspace so the entrypoint can run `drizzle-kit`
migrations before `next start`. Neither executes there. The honest severity is **present on the
server, not running**: a supply-chain surface rather than a live vulnerability, and a real argument
for `output: standalone` whenever somebody revisits that trade-off.

**The sealed-box placeholder is published on purpose**, which is a different claim from "it is not a
secret", so it is worth being precise. `packages/db/src/sealed-box.ts`'s `masterKeysFrom` **refuses
this exact value when `DEPLOY_ENV` is production** — so pasting it into a deployment is a process
that will not start, rather than a database of customer provider keys that anyone on the internet
can open. Three copies of it exist and `apps/web/e2e-env.test.ts` pins them together.

### The finding id is not gitleaks' fingerprint, and that is deliberate

gitleaks' own fingerprint is `commit:file:rule:line`. A baseline keyed on that goes stale every time
the surrounding file is edited, and a baseline people regenerate on every commit is a rubber stamp.

The id here is **rule + path + a SHA-256 of the matched text**, truncated. So a fixture that moves
within its file stays accepted, a fixture that moves to a different file re-fires, and **changing the
value re-fires** — which is the case that matters. `packages/db/src/provider-keys.test.ts` proves the
point: gitleaks reports it at line 21, where the file now has something else entirely.

## 4. Licences — 17 findings became 8, and the other 9 were not baselined

EPIC-007's report closed with an open question:

> **17 real, pre-existing private-package licence findings** … now show as warnings on every
> compliance run … **worth an actual look rather than permanent background noise**.

This is the actual look.

**Nine of the seventeen were permissive licences the allow-list had never been told about** —
`MIT-0` (3), `BlueOak-1.0.0` (5), `CC0-1.0` (1). MIT-0 is MIT without the attribution clause;
BlueOak-1.0.0 is OSI-approved and was written to read more clearly than MIT; CC0-1.0 is a
public-domain dedication. None is a concern, so none was baselined: all three went into
`ALLOWED_LICENSES` in `scripts/license-gate.mjs` and those nine warnings are gone for good.
**A baseline entry is for something accepted despite being a concern**, and using one for a licence
nobody objects to is how a list becomes something people skim.

The remaining eight are accepted with reasons and a March review date:

| licence | ids | why it is accepted |
|---|---|---|
| MPL-2.0 | `@axe-core/playwright:MPL-2.0`, `axe-core:MPL-2.0`, `lightningcss:MPL-2.0`, `lightningcss-darwin-x64:MPL-2.0` | File-level copyleft. It obliges whoever **modifies** a covered file and distributes it. We modify none of them, axe ships in nothing, and lightningcss is a build tool whose *output* is our CSS — MPL covers the covered files, not what a program built with them produces. |
| LGPL-3.0-or-later | `@img/sharp-libvips-darwin-x64:LGPL-3.0-or-later` | The strongest here and still not an obligation we trigger. LGPL's relinking requirement bites on **distributing** a linked work; this is a prebuilt binary invoked as a tool during a build whose output is images, installed from npm unmodified under its own licence. |
| FSL-1.1-MIT | `@sentry/cli:FSL-1.1-MIT`, `@sentry/cli-darwin:FSL-1.1-MIT` | Source-available with a competing-use restriction, converting to MIT two years after each release. We are not building an error-tracking product. The only non-OSI licence in the tree, which is why it gets six months rather than a year. |
| CC-BY-4.0 | `caniuse-lite:CC-BY-4.0` | A content licence on content: a browser-support dataset, not code. Its obligation is attribution, discharged by `/legal/third-party-notices`. Kept as an entry rather than allow-listed because CC-BY on a **code** dependency would be a real question and this gate should keep asking it. |

**Four of these are platform-specific** — `lightningcss-darwin-x64`, `@img/sharp-libvips-darwin-x64`
and `@sentry/cli-darwin`. A run on Linux will report that platform's variants as new and these as
stale. **That is the audit working**, not a defect: the dependency set really is different there,
and somebody should see that rather than have it normalised away by a clever id.

## 5. The licence headers — 102 files, and a gate that was looking at four packages

`scripts/license-gate.mjs` has treated *"an Apache-2.0 SPDX header appearing on a file inside a
proprietary package, which is a grant by accident"* as a **hard failure** since EPIC-007. It checked
`packages/ui`, `packages/db`, `packages/logger` and `apps/worker`. `REUSE.toml` declared **eight**
trees proprietary, and ADR-002 §1 names `docs/` among them in as many words.

Reading `reuse spdx` per tree found **102 files inside proprietary trees declaring Apache-2.0**:

| tree | files |
|---|---|
| `docs/` | 91 |
| `scripts/` | 6 |
| `apps/web` | 2 |
| `.githooks/` | 1 |
| root (`SECURITY.md`, `TRADEMARKS.md`) | 2 — **deliberate**, both ship to the public mirror |

**Why it is a real grant and not a formatting slip.** REUSE's default precedence is `closest`, so a
file's own header beats `REUSE.toml`'s glob. Those 100 files were genuinely Apache-2.0 while
`README.md` said in as many words that `docs/` and `scripts/` are all rights reserved. The
repository was public for a period in September 2026. Correcting a header does not un-publish what
was seen — `README.md` says that too — so this is forward-looking, and the epic's report says so
rather than implying otherwise.

**What changed:**

- The boundary check now reads its tree list **out of `REUSE.toml`** instead of a hardcoded array,
  so the gate and the licence declaration cannot disagree again.
- `.githooks/**` was added to `REUSE.toml`. It was covered by no glob at all, and its one file
  satisfied REUSE with a permissive header of its own.
- **96 headers corrected.** `docs/epics/plan-EPIC-000.md` needed a header *added* rather than
  changed: it had none, and REUSE was reading a fenced code block on line 109 — an example of what a
  public file's header looks like — as the file's own declaration.
- **Four are not corrected**: `docs/decisions/ADR-005`, `ADR-006`, `GATE-3.md` and `GATE-5.md`.
  `CLAUDE.md`'s never-touch list covers `docs/decisions/*`. They are named one by one in
  `HEADER_EXEMPT`, and EPIC-901's report §8 asks Soroush to correct them.

### Two traps on the way, both of which this repository had already paid for once

1. **Prose about a header is not a header.** The first version matched any occurrence of the string
   and flagged four files that merely *describe* a header, `scripts/license-gate.mjs` among them.
   EPIC-056 shipped exactly this bug and its own gate caught it (`7f8b67f`). The check now
   reproduces REUSE's algorithm — first declaration on a line of its own, after the spans REUSE is
   told to skip — and `apps/web/license-gate-boundary.test.ts` asserts both shapes.
2. **`git ls-files` reads the index, so a new file is invisible.** The real-tree assertion was
   verified by flipping a header and watching it fail — and it **passed**, because the file was new
   and untracked. That is `docs/PROCESS.md`'s failure 2 from "Local green is not CI green", where
   `binary-files.mjs` reported "486 checked" over a set that did not include the file with the NUL
   byte in it. The scan is now the same three-way union `binary-files.mjs` uses: tracked, staged, and
   untracked-but-not-ignored. With that, the control fails as it should.

## 6. Keys — there was no inventory, and now there is

`docs/security/key-inventory.md` lists all 25 credential-bearing environment names, where each
lives, who can rotate it and how. The `key-inventory` check compares that document with the tree
**in both directions**, so a name the code uses and the document does not list fails the audit, and
a row nothing uses fails it too.

**Last rotated is `never recorded` for every row.** No rotation has been performed or logged since
the project began on 2026-08-26, and nothing recorded when any value was first set. That is a
finding, not a formatting choice, and the column starts being useful at the first rotation.

**Rotating any of them is Soroush's** — `docs/AUTONOMOUS.md` puts production and its environment
variables out of reach, and on 2026-09-13 eleven production environment variables were overwritten in
one paste. Three rows need reading before anyone touches them: `BETTER_AUTH_SECRET` invalidates every
live session; `KEY_ENCRYPTION_SECRET` re-encrypts nothing, so rotating it without a migration makes
every stored customer provider key unreadable; and `R2_SECRET_ACCESS_KEY` is what the nightly backup
loop authenticates with.

## 7. What this audit did not cover

- **Anything running.** Every check reads this repository. Nothing connected to staging or
  production, so nothing here says whether a value in Coolify matches the one in a provider's
  console, or whether a deployed container is running the code that was audited.
- **The hand-written SHA-256.** `packages/core/src/artifact/sha256.ts` addresses every build and is
  read by two SDKs in two languages. It has never been reviewed by anyone who did not write it —
  EPIC-057's report §8 lists it first among what an external review hour should cover, and that hour
  needs a person.
- **The database's contents.** Customer provider keys are sealed under `KEY_ENCRYPTION_SECRET`;
  `docs/security/byo-key-threat-model.md` is the document for those.
- **Whether a baselined finding stays harmless.** An acceptance is a judgement with a date on it.
  Three of the four groups above come back in March or December.
